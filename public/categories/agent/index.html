Multi Agent Architecture: DAG vs Mailbox

Multi-Agent 的两种调度架构：DAG vs Mailbox 假设我们正在开发一个 Coding Agent，希望它能同时派出多个 Subagent：一个分析代码，一个检查测试，最后再汇总结果。 并发启动多个 Agent 并不难，但很快会遇到几个问题： 有些任务依赖其他任务的结果，如何安排执行顺序？ 如果执行中途崩溃，如何恢复，又如何避免重复执行？ 如果两个 Subagent 在执行过程中需要相互沟通，怎么办？ 这些问题引出了 Multi-Agent 的两种架构思路：基于 DAG 的中心化调度（Maka），以及基于 Mailbox 的消息驱动协作（Codex）。 一、DAG：将 Subagent 组织成工作流 1. 核心思路 首先，将每个 Subagent 抽象成一个任务执行单元（Operator）：接收明确的任务描述和上下文，独立执行，最后返回结果。 随后，由 Main Agent 将任务组织成 DAG，描述任务之间的依赖关系。 例如：A、B 可以并发执行，但 C 必须等待 A、B 的结果。 很自然地，我们可以引入一个 Coordinator（调度器），专门根据 DAG 判断哪些任务可以执行，并启动对应的 Subagent。 这样就实现了职责分离： Main Agent：负责规划任务，决定做什么。 Coordinator：负责依赖调度，决定何时执行。 Agent Runtime：负责真正运行 Subagent。 但这只是最基础的方案。实际的 Agent 任务可能运行很久，中途还可能修改计划、发生异常。因此，Maka 又引入了四个关键设计。 2. 四个核心设计 ① Durable Intent：任务计划需要持久化 首先，Agent 的任务计划并不总能一次性确定。 例如，A 在调查代码时发现一个新问题，需要新增任务 D。也就是说，DAG 需要支持动态修改。 另外，如果任务执行一半程序崩溃，之前的计划也不应该丢失。 ...
