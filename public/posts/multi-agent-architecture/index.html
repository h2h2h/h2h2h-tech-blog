Multi-Agent 的两种调度架构：DAG vs Mailbox#

假设我们正在开发一个 Coding Agent，希望它能同时派出多个 Subagent：一个分析代码，一个检查测试，最后再汇总结果。

并发启动多个 Agent 并不难，但很快会遇到几个问题：

  • 有些任务依赖其他任务的结果，如何安排执行顺序？
  • 如果执行中途崩溃，如何恢复，又如何避免重复执行？
  • 如果两个 Subagent 在执行过程中需要相互沟通，怎么办？

这些问题引出了 Multi-Agent 的两种架构思路：基于 DAG 的中心化调度（Maka），以及基于 Mailbox 的消息驱动协作（Codex）。

一、DAG：将 Subagent 组织成工作流#

1. 核心思路#

首先，将每个 Subagent 抽象成一个任务执行单元（Operator）：接收明确的任务描述和上下文，独立执行，最后返回结果。

随后，由 Main Agent 将任务组织成 DAG，描述任务之间的依赖关系。

例如：A、B 可以并发执行，但 C 必须等待 A、B 的结果。

很自然地，我们可以引入一个 Coordinator（调度器），专门根据 DAG 判断哪些任务可以执行，并启动对应的 Subagent。

这样就实现了职责分离：

  • Main Agent：负责规划任务，决定做什么。
  • Coordinator：负责依赖调度，决定何时执行。
  • Agent Runtime：负责真正运行 Subagent。

但这只是最基础的方案。实际的 Agent 任务可能运行很久，中途还可能修改计划、发生异常。因此，Maka 又引入了四个关键设计。

2. 四个核心设计#

① Durable Intent：任务计划需要持久化

首先，Agent 的任务计划并不总能一次性确定。

例如，A 在调查代码时发现一个新问题，需要新增任务 D。也就是说，DAG 需要支持动态修改。

另外，如果任务执行一半程序崩溃，之前的计划也不应该丢失。

因此，Maka 将 Main Agent 提交的任务计划持久化到 SQLite，并通过追加 Schedule Revision 的方式记录每次修改。

这样既能恢复计划，也能追溯整个 DAG 的演进过程。

② Reconciliation：如何恢复并推进任务状态？

有了持久化计划，接下来的问题是：程序重启后，如何知道哪些任务已经完成、哪些还可以继续执行？

Maka 借鉴了 Kubernetes Controller 的 Reconciliation 思想。

Coordinator 不将内存中的 DAG 作为权威状态，而是根据 SQLite 中的调度记录和 Runtime 的执行记录，反复进行：

读取持久化事实 → 重建 DAG 状态 → 计算可执行节点 → 推进调度。

这样，即使 Coordinator 崩溃，也能在恢复后重新计算下一步动作。

此外，它采用事件驱动的 Single-Flight Driver：

  • 计划修改、子任务执行事件等触发重新计算，而非不断轮询。
  • 同一张 DAG 同时只运行一个协调 Driver，重复触发可以合并。

注意，这并不限制多个 Subagent 并发运行，只是避免调度过程本身发生不必要的并发竞争。

③ Claim：如何避免重复启动 Subagent？

这里还有一个问题：

DAG 的依赖状态可以反复计算，但启动 Subagent 是可能产生副作用的操作。

假设任务 A 已经启动，并修改了部分文件，此时 Coordinator 崩溃。重启后再次发现 A 满足执行条件，如果直接创建新 Run，就可能重复执行之前的操作。

因此，Maka 引入 Claim（执行认领）。

在首次启动前，将任务意图与确定的 Session、Turn、Run 等执行身份原子绑定并持久化。

后续即使重复调度，也会检查或恢复原来的 Run，而不是无条件创建一个新的执行实例。

需要注意：Claim 保证的是执行准入和身份的幂等性，并不能保证 Subagent 内部的所有副作用都只发生一次。

④ Supervisor：如何让 LLM 与确定性调度解耦？

Coordinator 可以根据 DAG 自动推进任务，但它无法判断复杂执行结果是否符合用户目标。

例如，Subagent 发现原技术方案不可行，应该如何重新规划？这仍然需要 LLM 决策。

Maka 的方案是：

  1. Main Agent 通过 update_agent_graph 提交计划。
  2. 通过 yield_agent_graph 结束当前 Turn，不必阻塞等待整个 DAG。
  3. Coordinator 在后台自动调度任务。
  4. 到达需要语义判断的检查点时，Host 唤醒 Main Agent。
  5. Main Agent 检查结果，决定修改 DAG 还是结束任务。

因此，Main Agent 不需要在每个 Subagent 完成后都介入，而是在真正需要语义决策时重新参与。

总结下来，Maka 的核心思想是：LLM 负责规划，程序负责调度；计划可以动态变化，执行状态必须可靠恢复。

二、Mailbox：让 Subagent 像 Actor 一样通信#

DAG 方案将协作关系集中在任务图中，但如果两个 Subagent 需要频繁交换信息呢？

例如，A 正在检查 Runtime，B 正在检查 Storage。A 发现一个与 Storage 有关的问题，希望直接通知 B。

在 Maka 的工作流模式下，新的任务调整通常需要通过 Main Agent 修改 DAG。

而 Codex 采用了另一种思路：每个 Agent 都拥有独立的身份、会话和 Mailbox，可以直接向其他 Agent 发送消息。

1. 用 Go Channel 理解 Mailbox#

如果熟悉 Go，可以近似把每个 Agent 看作一个 Actor，拥有自己的消息入口：

Agent = Session + Mailbox + Runtime

其他 Agent 可以向它发送消息，Runtime 则负责在适当时机处理这些消息。

不过，Codex 的 Mailbox 并不是简单的 chan Message，实际更接近：

Mailbox = 消息队列 + 变化通知

  • Mutex<VecDeque>：保存真实消息。
  • Tokio watch：通知 Mailbox 有新活动。

用 Go 类比，就是一个受 Mutex 保护的消息队列，配合一个通知 Channel。

这种设计将消息存储和唤醒信号分离。即使多次通知被合并，真实消息仍然保留在队列中。

2. 收到消息，不代表立即启动 LLM#

这是 Mailbox 设计最重要的细节。

Codex 将消息投递与执行触发分开：

  • send_message：只将消息放入 Mailbox，不主动启动新 Turn。
  • followup_task：发送消息，同时请求目标 Agent 启动新的 Turn。

而且，如果目标 Agent 正在执行 LLM Sampling，新消息也不会强行改变已经发送的模型请求，而是在后续合适的执行边界进入上下文。

子 Agent 完成任务后，也可以通过完成通知将结果送回父 Agent 的 Mailbox。

所以，消息入队、消息被消费、LLM 开始执行，是三个不同的事件。

这与 Go Channel 有一个明显区别：接收消息的 goroutine 可以直接继续运行，但 Agent 的一次 LLM Turn 具有独立的生命周期，需要 Runtime 显式管理。

3. 为什么这种方案更适合动态协作？#

在 Mailbox 模型中，Agent 可以根据其他 Agent 的消息不断调整行为，而不要求所有通信都事先体现为 DAG 依赖。

例如：

A 发现问题 → 给 B 发送消息 → B 调整调查方向 → B 将结果发给 A 或 Main Agent。

协作关系是在执行过程中通过消息逐步形成的。

这带来了更大的灵活性，但也意味着全局协调状态分散在多个 Agent 的会话和消息历史中，执行过程的追踪、恢复和一致性管理可能更加复杂。

三、最终如何选型？#

维度DAGMailbox
核心抽象OperatorActor
协作方式全局 DAG 编排Agent 间消息通信
依赖关系显式声明动态形成
执行驱动Coordinator 调度消息与 Turn 调度
主要优势确定性、可观测、易恢复灵活、适合动态协作

如果任务相对明确，依赖关系容易描述，而且重视可靠执行与故障恢复，DAG 更合适。 例如自动化代码审查、批量分析、长流程任务执行。

如果任务具有探索性，需要多个 Agent 频繁沟通、协商和调整方向，Mailbox 更自然。 例如多个 Agent 协作设计架构或联合解决复杂问题。

当然，两者并不互斥：可以使用 DAG 管理宏观任务阶段，再通过 Mailbox 支持阶段内部的动态协作。

最后，用两句话概括两种架构的本质区别：

  • DAG：Coordination lives in the Graph. 协调关系存在于全局任务图中。
  • Mailbox：Coordination lives in the Conversation. 协调关系更多地存在于 Agent 之间的消息交互中。

Multi-Agent 架构选型的关键，并不是如何运行更多 Agent，而是应该把协作控制权集中在任务图中，还是分散到各个 Agent 的通信过程中。
